## 1. Ranked findings

All behavioural findings are **NEW** in this range: `host/update.js` did not exist before `2de5c4d`,
and the Cursor state-database reads are new in the uncommitted work. Status is given per pass.

### F1 — NEW, Medium (FIXED in the frozen tree, re-verified): the updater wrote (and on rollback deleted) outside the plugin directory through a pre-existing directory junction

Pass 1 evidence (HEAD):

- `host/update.js:768` `const backupTarget = join(backupDir, entry.path)`, `host/update.js:770`
  `copyFileSync(target, backupTarget)`, `host/update.js:787` `renameWithReplace(staged, target)` with
  `target = join(directory, entry.path)` (`:765`, `:785`). Every join is lexical; HEAD has no
  `realpath`/containment check anywhere (grep for `realpathSync` in HEAD's `host/update.js`: none).
- Rollback: `host/update.js:711` `rmSync(target, { force: true })` for a newly created file and
  `host/update.js:712` `copyFileSync(join(backupDir, relativePath), target)` for a replaced one.

Repro (`verify/.tmp-audit/update-attacks.mjs` probe 2d on the HEAD tree): temp plugin directory with
`symlinkSync(outside, join(plugin,'link'), 'junction')`; manifest `1.1.0` listing `link/escape.txt`
plus `package.json`; serve matching bytes/hashes. HEAD returns
`{"ok":true,"from":"1.0.0","to":"1.1.0",...,"reload":"restart-required"}` and `<outside>/escape.txt`
exists. `verify/.tmp-audit/junction-rollback.mjs` additionally showed the failed-apply path restoring a
file outside (`ORIGINAL OUTSIDE BYTES`) and deleting a newly created outside file while the inside
tree was restored.

Pass 2 status: **FIXED**. `host/update.js:792` `checkTargetContainment`, called at `:866` before
staging, `realpath`s every target's deepest existing ancestor and requires it inside
`realpath(directory)`; failures are `target-containment-failed` (`:796`) / `target-escapes-plugin`
(`:809`). `verify/.tmp-audit/final-harden.mjs` (8/8) proves: a direct junction, a junction nested
under a new subdirectory, and the rollback-path manifest are all refused with one of those named
errors; the outside directory is unchanged/absent, the plugin tree hash is unchanged, and no staging
or backup directory is created. The probe also asserts the new `target-is-link` preflight does **not**
mask this error for a junction used as a parent directory (containment still wins).
`verify/.tmp-audit/update-attacks.mjs` is 27/27 including the junction probe.

### F2 — NEW, Low/Medium (FIXED in the frozen tree, re-verified): at HEAD, `applyUpdate` never cross-checked the shipped `package.json` version against `manifest.version`

Pass 1 evidence (HEAD): `host/update.js:899-916` verifies downloaded bytes/hashes and goes straight to
`writeFiles`: no `missing-package-json` / `version-mismatch` branch exists, and the downloaded
`package.json` is never read. The committed contract states the guarantee that makes this safe
(`docs/update.md:21-25`: the builder always includes `package.json` and its version must equal the
manifest version, "否则升级完成后 readCurrentVersion 读到的还是旧版本，页面会一直提示有同一个更新"),
but that is enforced only by `verify/build-update-manifest.mjs --check`, not by `applyUpdate` on the
manifest it downloads.

Repro (`verify/.tmp-audit/versions-contract.mjs` on the HEAD tree):

```
CASE missing-package-json ok=true error="" reportedTo="1.1.0" installedVersionAfter="1.0.0"
CASE version-mismatch   ok=true error="" reportedTo="1.1.0" installedVersionAfter="1.0.5"
CONTRACT_HOLDS=0
```

Impact: a served manifest could omit `package.json` (apply succeeds; installed version stays old, so
the page keeps offering the same update) or ship a `package.json` version that disagrees with the
manifest (the success payload reports `to` = manifest version while the installed bundle reports
something else). Not a privilege escalation, but exactly the untrusted-input case under audit.

Pass 2 status: **FIXED** in the final tree. `host/update.js:279` `readShippedVersion`, with the
requirement checked after download+hash verification and before the first write (`:1064`
`missing-package-json`, `:1068` no readable version and `:1071` mismatch both `version-mismatch`).
`verify/.tmp-audit/final-harden.mjs` (8/8) proves both refusals leave the tree byte-identical with no
staging/backup, an unreadable shipped version is refused as `version-mismatch`, and a manifest that
ships the matching `package.json` still applies. `versions-contract.mjs` now prints
`CONTRACT_HOLDS=1`.

### F3 — NEW, Low/Informational (FIXED in the final frozen tree, re-verified): a file symlink inside the plugin directory used to be followed when the backup was made

Pass 1 evidence (HEAD): `host/update.js:768-770` `statSync(target).isFile()` and
`copyFileSync(target, backupTarget)` follow a file symlink, so the target's bytes outside the plugin
directory are copied into `.update-backup-*`. The replacement itself does not write through the link
(the symlink is replaced). Same preconditions as F1 (a symlink planted inside the plugin directory,
plus manifest control), and the module's stated trust model already grants a compromised manifest code
execution, so this was defence-in-depth rather than a new privilege.

Pass 2 status: **FIXED**. `host/update.js:836-851` `checkTargetsAreNotLinks` runs before the staging
directory is created (`:868`, after containment) and uses `lstatSync` (never `statSync`/`existsSync`):
a Symlink/Junction target returns `target-is-link` (`:847`), any lstat failure other than ENOENT
returns `target-inspection-failed` (`:844`). The backup phase re-checks with `lstatSync` (`:900-908`)
and throws "... became a symbolic link after validation; refusing", reported as `backup-failed`.

Repro (`verify/.tmp-audit/link-frozen.mjs`, 6/6 on the final tree):

- a pre-existing file symlink target, a dangling symlink, and a directory junction used as the target
  are all refused with `target-is-link` before any write: no `.update-*` directory is created, the
  outside file is unchanged, the symlink target's bytes are nowhere under the plugin directory (the
  probe scans every file for `OUTSIDE-SECRET-BYTES`), and the plugin tree hash is unchanged;
- a normal regular-file apply still succeeds afterwards (positive control).

Residual, documented as UNVERIFIED: the backup-phase race (a local actor swapping a regular target for
a link after the preflight) is code-reviewed only; `writeFiles` is synchronous, so there is no
deterministic interleaving point from the public API. On this Windows host an `lstat` through a
regular-file ancestor reports ENOENT, so the `target-inspection-failed` branch is code-verified only
(the probe records a clean `replace-failed` with the tree byte-identical instead; no outside access).
The earlier 11:26:54 snapshot had this finding OPEN.

### F4 — NEW (FIXED at the route level; accepted limitation remains in the module): no internal deadline on the update network path

Pass 1 evidence (HEAD): `host/update.js:120` `let applying = false`, `:836-841` flag set before any
await, reset in `finally`; `host/update.js:482-510` `requestBytes` calls `fetchImpl` with only the
caller's signal and no timer; HEAD `index.js:1586-1591` passed no signal. A hung manifest fetch held
the module-wide flag (observed: second `applyUpdate` returned `already-running` after 300 ms).

Pass 2 status: **route-level deadline added and verified**, module-level limitation accepted.
`index.js:453` `export const UPDATE_TIMEOUT_MS = 120000`; `updateCheckPayload` (`:1580-1601`) and
`updateApplyPayload` (`:1611-1637`) create an `AbortController`, arm `setTimeout(..., UPDATE_TIMEOUT_MS)`,

`setTimeout`/`AbortController` in the module), so a caller of the exported API directly can still hold
the flag with a hung fetch; per the Lead this is recorded as an accepted limitation of the module, not
a route defect.

## 2. UNVERIFIED / limitations

- **Rollback hole in `renameWithReplace` (not reproduced).** `host/update.js:681-695` (HEAD; frozen
  `:711-722`): the fallback unlinks the target and renames again; if the second rename fails after the
  unlink succeeded, that entry was never pushed to `replaced` (`:788` HEAD / `:929` frozen), so
  `rollbackFiles` cannot restore it and a failed apply would leave that original missing. I could not
  force "unlink succeeds then second rename fails" through the public API; on this platform a locked
  target makes the unlink fail first. UNVERIFIED, theoretical.
- **Backup-phase link race (code-reviewed only).** The `lstatSync` re-check in the backup phase
  (`host/update.js:900-908`) closes the window where a local actor swaps a regular target for a link
  after the preflight. `writeFiles` is synchronous, so no deterministic interleaving point exists from
  the public API; the dynamic race is UNVERIFIED.
- **`target-inspection-failed` branch (code-reviewed only on Windows).** An `lstat` through a regular
  file ancestor reports ENOENT on this host, so the "non-ENOENT lstat failure" branch could not be
  triggered dynamically; the probe instead records a clean `replace-failed` with the tree
  byte-identical. No outside access in either case.
- **Cache identity residuals.** The scan-cache key is harness + path + size + mtimeMs + ctimeMs plus
  (for Cursor) the state-database stamp. A rewrite that preserves all of those exactly would be served
  stale. Not reproduced; documented design.
- **Cursor WAL and the stamp.** The frozen `host/foreign/cursor.js:220-238` deliberately excludes the
  `-wal` from the stamp (it churns while Cursor runs; including it would invalidate every cached row on
  every scan). Consequence: an existing conversation whose cwd/model changed only in a not-yet-
  checkpointed WAL would keep its cached row until the main DB file changes. A brand-new conversation
  always misses the cache (no transcript cache entry yet), so it is read fresh. Not reproduced
  (existing conversations' workspace/model are not rewritten in the normal flow); Low/UNVERIFIED
  design tradeoff.
- **`readCappedBody` arrayBuffer fallback.** If a `Response` has no `body.getReader` (test doubles
  only; real `fetch` always streams), the fallback buffers the whole body before the size check. Not
  reproducible with real `fetch`; UNVERIFIED for a hypothetical non-streaming transport.
- **Client UI (chooser cascade, update gate, foreign parent cascade).** The audit re-ran the existing
  React-driven suites (`client-check.mjs`, `adversarial-client.mjs`) and pin-checked the relevant
  source markers, but did not independently re-drive the React tree; those results are the suites'
  evidence, not this audit's.
- **Route deadline duration.** The abort wiring is proven by firing the timer early; the real 120 s
  wall-clock behaviour was not waited out.
